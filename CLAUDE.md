# CLAUDE.md

This file gives Claude Code the context needed to work effectively in
`cloudnative-pg/cnpg-infra` — the admin tooling for the `cloudnative-pg`
GitHub organization itself (repo settings, teams, CODEOWNERS), not a
product or docs repo. See the top-level `cnpg.io/CLAUDE.md` for how this
repo fits into the wider workspace of org-control repos.

## Project overview

Everything here is read by a human running `gh`-based bash scripts from
their own laptop — deliberately never from CI (see README's "Philosophy:
laptop, not CI"), so an org-admin-scoped credential never has to live in a
pipeline secret. There is no build, no test suite, no deploy step: the
"artifacts" are real GitHub org state (branch rulesets, team membership,
repo descriptions, CODEOWNERS), and the YAML files here are the desired
state that state gets reconciled against.

## Architecture: generated vs. hand-maintained

- **`generated/*.yaml`** (`managed-repos.yaml`, `teams.yaml`) — rebuilt
  from live GitHub state by `update-managed-repos.sh` / `update-teams.sh`.
  Never hand-edit; a run overwrites the file completely.
  `generated/managed-repos.yaml` is the **allowlist** — every script
  refuses to touch a repo that isn't listed there.
- **Hand-maintained policy files** (repo root) — human judgment calls,
  each with a `reason` explaining *why*, not regenerated by anything:
  - `repo-tiers.yaml` — every managed repo's importance `class` (A/B/C),
    governance `subproject`, optional `description` override, and
    `owners:` (the desired membership of that repo's `<repo>-owners`
    GitHub team — see below). The only policy file where *every* managed
    repo gets an entry, since every repo has some class and some owners.
  - `componentowners-policy.yaml` — desired CODEOWNERS content per repo:
    an ordered list of `path` rules, each with `teams`/`users`. This is
    the source of truth `check-repo-settings.sh` audits against and
    `scripts/render-codeowners.rb <repo>` renders to stdout as real
    CODEOWNERS file content — it does **not** carry per-team membership;
    that lives in `repo-tiers.yaml`'s `owners:`.
  - `org-policy.yaml` — rules identical across every repo instead of
    repeated 32 times: `global_admin_teams` (`admins`) and
    `global_maintain_teams` (`bots`) get that floor permission granted on
    every managed repo, enforced by `fix-repo-settings.sh`.
  - `repo-policy.yaml` — per-repo exceptions: `category: automated` (skip
    the review-count/code-owner-review floor — bot-published content, e.g.
    `docs`, `api`, `artifacts`), `required_reviews` override,
    `ruleset_bypass_teams` (teams that bypass the branch ruleset entirely
    — `always` mode, direct push + review-free merge — for release
    automation), `pages_*` (documented Pages config, not enforced).

Adding an entry to any hand-maintained file is an operational call about
that one repo, not a governance decision — no vote needed, just a clear
`reason`. Don't hand-edit a `generated/*.yaml` file; re-run its script.

## The `<repo>-owners` team model

Every managed repo (with rare exceptions, see below) has a dedicated
`<repo>-owners` GitHub team, referenced first in that repo's CODEOWNERS
`*` rule in `componentowners-policy.yaml`. `repo-tiers.yaml`'s `owners:`
field is the *only* place that team's membership is declared —
`componentowners-policy.yaml` never lists individual users for a repo
that has an owners team. `scripts/sync-project-owner-teams.sh` reconciles
GitHub to match: creates the team if missing, adds anyone listed but not
yet a member, **and removes anyone who is a member but no longer listed**
— `repo-tiers.yaml` is authoritative desired state, not just a floor.

Team naming: `<repo>-owners`, with a leading `.` stripped rather than
turned into a leading `-` (`.github` → `github-owners`, not
`-github-owners`, which GitHub would reject as an invalid slug).

A repo with no `owners:` entry (or an empty one) falls back to whatever
other teams `componentowners-policy.yaml` lists for it (typically
`maintainers`). Special case: `admins` cannot be used as an
owners-team-style GitHub Team reference for ruleset bypass — see below.

**Known trap, hit once already**: removing a *CODEOWNERS reference* to a
team (e.g. dropping `maintainers` from a repo's `*` rule) does **not**
revoke that team's actual repo permission — CODEOWNERS only gates review
requirements, it is a completely separate mechanism from repo access.
After any CODEOWNERS restructuring, check `check-repo-settings.sh`'s
"Teams" line for stale grants left over from before the change (this is
exactly how `maintainers` was found still holding `maintain` on
`cloudnative-pg`, and `extensions-maintainers` still holding `push` on
`postgres-extensions-containers`, long after CODEOWNERS moved away from
referencing them).

**Pending-invite trap**: adding someone to a team who isn't already a
full org member creates a *pending* invitation, not active membership,
until they accept. Never remove a person's *direct* collaborator grant
in the same pass as adding them to a team unless `is_active_org_member()`
confirms they're already active — otherwise they lose real access for
however long the invite sits unaccepted.

## Landing a rendered CODEOWNERS file in a target repo

`scripts/render-codeowners.rb <repo>` only prints the desired content —
it never touches the target repo's clone or GitHub state. To actually
land it: write the output to `<repo>/CODEOWNERS`, commit, and open a PR
in *that* repo (DCO sign-off, Conventional Commit, `Assisted-by:`
trailer). Unlike `cnpg-infra` itself, a target repo normally has no
PR-bypass exception, so don't push straight to its default branch even
though `cnpg-infra`'s own workflow does that for its own changes — see
"cnpg-infra's own repo is a deliberate exception" below; that exception
is scoped to this repo alone.

## Branch protection: rulesets only, not classic protection

Every managed repo now enforces its default branch via a GitHub Ruleset
named after that branch (e.g. `main`), not classic branch protection —
**don't assume that branch is `main`**: `fix-repo-settings.sh` reads the
repo's actual default branch and names/targets the ruleset accordingly
(`kopia`'s default branch is `klio`, so its ruleset is named `klio`, not
`main` — check `default_branch` before reasoning about "the main
ruleset" for any given repo). Classic branch protection was found to
silently ignore writes to `allow_force_pushes` on at least one real
repo, and as of this migration no managed repo has classic protection
active anymore.
`fix-repo-settings.sh` only ever raises the floor (required reviews,
code-owner review, force-push/deletion block, linear history) and never
lowers an existing stricter value; it also now force-creates the ruleset
even when nothing needs raising, so "no gap to fix" doesn't mean "no
ruleset" — full migration to rulesets was the actual goal, not just
floor enforcement.

Ruleset gotchas (all discovered the hard way, worth re-reading before
touching the ruleset-building code in `fix-repo-settings.sh`):
- `required_status_checks[].integration_id` must be **omitted** entirely
  for a check with no known integration — the API rejects
  `"integration_id": null` outright (422), even though it silently
  accepts the key being absent.
- `bypass_actors` needs a **numeric team id**, not a slug — but a
  `secret`-privacy team (e.g. `admins`) cannot be used as a `Team` bypass
  actor at all ("must be part of the ruleset source or owner
  organization"). Use `actor_type: "OrganizationAdmin"` (no id needed)
  to mean "org admins/owners" instead.
- `bypass_actors` is not automatic for org owners/admins the way classic
  protection's `enforce_admins: false` was — it has to be explicitly
  configured per ruleset.
- The ruleset API needs a full-body PUT/POST, not a partial patch.

## cnpg-infra's own repo is a deliberate exception

Per standing instruction: **do not open PRs against this repo** — push
directly to `main`. This project is experimental. That only works because
`repo-policy.yaml` gives `cnpg-infra` a `ruleset_bypass_teams: [admins]`
entry (rendered as an `OrganizationAdmin` bypass, per the secret-team trap
above) — if that entry is ever removed, direct pushes will start being
rejected by the repo's own ruleset. Don't "fix" this bypass as a drive-by
security cleanup without checking with Gabriele first.

## Workflow conventions

- Every settings-mutating script defaults to dry-run and requires an
  explicit `--apply`. Always show the dry-run diff and get explicit
  go-ahead before re-running with `--apply` — don't chain straight from
  "let me check" to `--apply` in the same turn, even for a repo the user
  already asked to fix.
- Only ever *raise* a setting to the floor; never lower an existing
  stricter value. This applies to review counts, team permissions
  (`global_admin_teams`/`global_maintain_teams`), and ruleset rules alike.
- DCO sign-off, Conventional Commits, and an `Assisted-by:` trailer for
  material AI assistance (blank line after `Signed-off-by:`, per
  `governance/AI_POLICY.md`) — same baseline as every other repo in the
  org.
- `jq`'s `//` operator treats a real `false` the same as `null`/missing —
  never use it to default a boolean; use
  `if . == null then <default> else . end` instead. This bug once made
  `fix-repo-settings.sh` silently flip a real `false` back to `true`.
